运行前设置 `SEO_SITE_PROFILE=/absolute/path/site.json`。使用 `seo.py init` 为目标站点创建显式配置；主机采用精确白名单，不自动扩展子域。默认使用通用网站规则；`business_profile: "bingx"` 为可选业务扩展，只有明确选择它才启用对应路由和市场参考逻辑。缺少 profile 时不进行线上采集。

默认交付本地报告或问题清单。只有用户明确要求外部发布并指定或确认目的地时，才调用相应飞书/外部工具写入；无需发布时不要求外部账户授权。所有输出、证据和状态库存放在技能目录之外，按站点隔离。示例、fixtures 和既有历史记录仅用于显式选择的离线演练，不自动导入真实报告。浏览器的通用就绪信号仅证明可见正文与有限稳定性，不证明业务实体正确；如提供身份/模板信号则保持这些更强要求。


# 017 · 修复复测

Python 3.10+标准库，依赖同级003 `seo-crawlability` v1.0.1+。只围绕指定原问题复测，不运行全站总调度，不修改生产或专业技能源台账。

## 执行

1. 取得原问题ID与源报告，读取规则、证据、原复现步骤、适用范围和未确认根因。用户指定的问题沿用ID，复发也不创建新ID。先明确这是“检查是否仍存在”还是“验证已部署修复”。
2. 用原问题对应专业技能选择验收条件，并考虑实际修复方式。内容保留、精确迁移、下线404/410有不同条件；不要以“必须返回200/必须补标题”验收本应下线的错误页。缺业务策略时可做症状探测，不能据此批准上线或关闭问题。
3. 确定部署时间及来源、原样本、同模板对照、设备/语言/参数/直达/站内进入/返回等受影响变体。原URL问题可以逐项验收；模板或未知范围即使所选样本全通过，也只报告部分通过。没有独立路由清单不能称整个模板完成。
4. 使用已授权浏览器或专业采集器重跑复现步骤，保存精确URL、实际设备与JS、进入方式、采集时间。部署验收必须取得新导航，记录完成导航的观察时点；读取旧标签页不能证明修复。间歇性问题需跨时间/新导航复测；相同采集时间的多个副本不算独立重复。
5. 阅读[证据合同](references/evidence.md)，保留原始JSON并绑定SHA。缺失、失败、环境错配和旧证据列为缺口。HTTP和DOM分别采集，不猜浏览器状态码；正文摘录不能证明某内容不存在。复杂语义/交互先由主责技能核验，确定性谓词仅验证明确的可观察条件，不能代替根因判断。
6. 按需要单独调用014–016刷新相关引擎。将真实平台报告作为engine_reports输入，原数据库时间仍保留。平台仍报、未检查该URL、快照已有但问题是否清除未知分别列出；200、已收录或列表缺席均不自动证明原内容/路由问题已修复。
7. 运行下面命令，审阅前后值及原始证据。`passed`仅表示明确URL与声明条件的修复验收通过；`partial_pass`表示部分条件或更大范围仍未覆盖；`failed`有新失败；`inconclusive`缺关键证据或存在冲突。引擎状态独立，默认需平台复核。把结果交018汇总并沿用原问题，不直接清除技能源台账。

```bash
python3 "<SKILL_DIR>/scripts/recheck_issues.py" --plan "<DATA>/plan.json" --state "<PERSISTENT>/recheck" --output "<NEW_REPORT_DIR>"
```

默认新快照24小时内；`--at`保留原时点重放，`--max-age-hours`调整时效。修复前基线可以较早，但必须与原问题证据绑定。0表示声明复测执行完整（可能全部失败），2表示部分执行/证据不足，1表示输入或执行错误。输出report.md/json、rechecks.csv、cases.csv、recheck-history.json/csv。每次用新输出目录，状态库持久复用。

## 边界

- `repair_verified`不等于全站无问题；缺部署时间时本次通过也不宣称修复已部署。
- 本版本关联014–016结构化报告，保守保留`engine_recovery_confirmed=false`；不会仅从平台快照推断后续重抓已经清除原问题。需要更强结论时另行取得原问题对应的引擎证据并审阅。
- 支持已保存HTTP/DOM JSON字段，不能直接把截图、LHR或任意工具的HTML交给JSON谓词。其他证据由主责技能采集/规范化并保留原证据链；不可为让测试通过手工伪造值或更改基线。
- 当前登记的是验收事件，不写入源问题的关闭状态；018统一呈现最新复测和平台差异。
