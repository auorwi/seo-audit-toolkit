运行前设置 `SEO_SITE_PROFILE=/absolute/path/site.json`。使用 `seo.py init` 为目标站点创建显式配置；主机采用精确白名单，不自动扩展子域。默认使用通用网站规则；`business_profile: "bingx"` 为可选业务扩展，只有明确选择它才启用对应路由和市场参考逻辑。缺少 profile 时不进行线上采集。

默认交付本地报告或问题清单。只有用户明确要求外部发布并指定或确认目的地时，才调用相应飞书/外部工具写入；无需发布时不要求外部账户授权。所有输出、证据和状态库存放在技能目录之外，按站点隔离。示例、fixtures 和既有历史记录仅用于显式选择的离线演练，不自动导入真实报告。浏览器的通用就绪信号仅证明可见正文与有限稳定性，不证明业务实体正确；如提供身份/模板信号则保持这些更强要求。


# 018 · 报告与飞书交付

Python 3.10+ 标准库，macOS/Linux；飞书发布使用已经授权的 `lark-cli` 用户身份。无需修改 001–017 的台账。这里是报告技能，不是全库总入口或定时器。

## 工作流程

1. 明确要汇总的证据期与来源。选择各专业技能的最终 report.json；001 使用 summary.json，017 使用复查 report.json。不要从同目录自动搜到旧版、控制样例或多个重放报告后全部当新检查。阅读[数据合同](references/contracts.md)，部分审查用 requested_skills 声明本次需要的技能。把源报告复制到本轮目录，计算实际 SHA256 并建立 manifest。
2. 区分“已有结果整理”和“重新巡查”。脚本输出始终标为现有审查结果汇总；需要新一周的巡查时，先独立运行用户选择的专业技能，再汇总其新产物。报告日期不能冒充平台更新时间。没有 CMS 权威全集就不宣称全站无遗漏。
3. 构建本地报告，持久复用同一个 state 目录。检查分类、首次/末次时间、精确URL、来源证据和复查。不同技能的相似症状不自动并根因；原ID相同但规则/URL冲突会停止。017沿用原ID附加，不重复建问题，不因为暂未出现/返回200/复查通过就自动关闭。未知原ID单列。
4. 从专业报告审阅修复方向、业务意图和优先级；自动摘要列出的“重点复查/确认观察”最多12条，只是索引，不是风险排名。完整台账保留所有条目。不能把HTML规范、访问性观察、环境受限性能数据统称索引阻断。
5. 仅当用户明确要求飞书交付并指定或确认目的地时，使用 lark-doc 技能，并先核对现有用户登录。发布前阅读[发布与恢复](references/publishing.md)。发布固定入口、按 run_id 命名的不可变报告和持续台账；每块写后回读全部文本与链接目标。来源 JSON 和 CSV 保存在本地产物，飞书摘要会明确截断；需要让其他人访问完整原证据时，另行通过已授权附件工具上传并回读，不能把本地路径当远程下载链接。
6. 默认交付本地产物；如用户要求的外部发布已成功回读，再交付相应入口链接和报告链接，说明仍未检查/被阻断的部分。同一次汇总重复发布使用相同 run_id、state、报告内容；必须复读通过才报告发布成功。

```bash
python3 "<SKILL_DIR>/scripts/report_seo.py" build \
  --manifest "<RUN>/manifest.json" --state "<PERSISTENT>/report" --output "<NEW_OUTPUT>"
# 仅在用户明确要求飞书发布并指定或确认目的地时执行：
python3 "<SKILL_DIR>/scripts/report_seo.py" publish \
  --report-dir "<NEW_OUTPUT>" --state "<PERSISTENT>/report"
```

build 仅整理本地证据，不触发平台抓取或飞书写入。0表示整理/发布成功，不表示网站健康；1表示输入/写入/回读错误。已有输出目录不可覆盖。测试使用临时目录和模拟远程传输；真实飞书验收另列，不能互相替代。

```bash
python3 -m unittest discover -s "<SKILL_DIR>/tests" -v
```
